# Windows Setup: release inputs and ordering

Run from `app/src-tauri` on the approved Linux build host with a private build/output directory, a release-specific Cargo target/cache (no concurrent candidate builders), the built frontend, approved core binary and expected SHA-256, and the approved toolchain. Use new output paths for each attempt. Do not synthesize a descriptor from NSIS-extracted or installed files. No tool here locates issuer keys or publishes a release.

1. **Build final role binaries.** Export an absolute, release-specific `CARGO_TARGET_DIR` (required) and private `TMPDIR` before running the script. Set `KAT_TOOLCHAIN_ENV` to the approved xwin env.sh (or use its existing `/opt/kat-windows-toolchain-20261027/env.sh` default), `KAT_BUILD_BIN_DIR` to a new absolute directory, `KAT_CORE_EXE` to the final absolute AMD64 core, and `KAT_CORE_SHA256` to its independently supplied release digest. Set approved `KAT_INSTALL_CORE_VERSION`, `KAT_INSTALL_CORE_SEQUENCE`, `KAT_INSTALL_CLIENT_SEQUENCE`. Run `sh scripts/build-windows.sh`. The normal binaries are frozen before the helper is built with their pins and the core pin. `role-hashes.txt` records the final six roles. Do not edit or PE-sign any role afterwards.
2. **Capture the uninstaller before signing the package.** `python3 scripts/build-setup.py capture --nsis-debs "$NSIS_DEBS" --output "$BUILD/Kat-Uninstall.exe"`. The directory must contain the two pinned Debian NSIS 3.11-1 packages. Only a disposable seed Setup is compiled; the hook retains its actual generated PE without executing it. This step does not use any package descriptor, issuer key or final Setup. If a release process separately Authenticode-signs the uninstaller, use those *final* bytes in step 3.
3. **Stage and describe.** `python3 scripts/stage-package.py prepare --bin-dir "$KAT_BUILD_BIN_DIR" --core "$KAT_CORE_EXE" --uninstaller "$BUILD/Kat-Uninstall.exe" --docs-dir "$CORE_RELEASE_DOCS" --build-identity "$BUILD/BUILD-IDENTITY.json" --source-revision "$FULL_REV" --payload "$BUILD/payload"`. Supply the real core release's `YAML.md` and `kat-client.example.yaml` and final BUILD-IDENTITY matching desktop/core executable hashes. The configured product version must match Cargo. The result contains the **unsigned** v0.2.28-compatible peer identity (`kat-package-auth.json`, schema 1), with SHA-256 of the six executable roles. Keep the private payload workspace immutable except for adding the following descriptors/signatures.
4. **Sign the bridge identity on the authorized issuer, not the build host.** `sign-update-manifest.py --kind package --manifest <absolute IPC JSON> --private-key <explicit issuer key> --signature <new IPC signature>`. Return `kat-package-auth.sig` next to the unchanged JSON. This signature authorizes **only peer authentication**, not installation.
5. **Describe all final installed bytes.** `python3 scripts/stage-package.py describe-setup --payload "$BUILD/payload"`. This produces `kat-setup-auth.json` (schema 2, product `kat-client-setup`): the complete nested IPC identity, and SHA-256 of the remaining 16 files (including the **exact** IPC JSON and signature). Review all release inputs/hashes and sign this separate document on the issuer with `sign-update-manifest.py --kind setup --manifest <absolute Setup JSON> --private-key <explicit issuer key> --signature <new Setup signature>`. Return `kat-setup-auth.sig`. Both signatures use the existing key and algorithm; no private inputs are needed on the build host. Do not rewrite even whitespace/line endings in the bridge files after this step. The schema-2 pair is not installed, so no hash cycle exists.
6. **Pack.** `python3 scripts/build-setup.py pack --nsis-debs "$NSIS_DEBS" --payload "$BUILD/payload" --output "$BUILD/Kat-Setup-x64.exe"`. The offline Rust product verifier checks both signatures, equality of **all** IPC identity fields (including version, revision and six role hashes) and all 22 installed file digests in a private snapshot. NSIS embeds those files and the two transient Setup authorization files. Installed size excludes the transient pair. Final NSIS embeds the checked uninstaller as a `File`; it does not regenerate it. `.build.json` records the successful gate. For a distribution ZIP, use `python3 scripts/stage-package.py archive --payload "$BUILD/payload" --output "$BUILD/Kat-Client-Windows-x64.zip"`. The outer release/update manifest binds the final Setup artifact after this step.

**Compatibility and trust boundaries:** The normal running v0.2.28 GUI continues to authenticate the new bridge using the original `kat-package-auth.json/.sig` names, exact schema-1 shape and role set; automatic authorized handoff is unchanged. Rollback caches and app/Runtime install inventories remain unchanged. Historical optional-watchdog identities are accepted only by the original peer-authentication policy. The new elevated Setup and final packer require the separately signed schema-2 authority **and** a matching independently signed six-role schema-1 identity. Neither a valid old descriptor nor a schema-2 document placed under the old name can substitute for this pair. A legacy installer that predates the fix is not upgraded by this policy. Existing version/sequence floors still apply; publish a properly versioned release, not a same-version rebuild with different hashes.
